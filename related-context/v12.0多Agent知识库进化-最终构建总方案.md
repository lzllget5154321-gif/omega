# v12.0 多 Agent 知识库进化 — 最终构建总方案

# 第一部分：完整讨论——我们知道了什么

## 1.1 三份研究的交集与分歧

```
用户独立研究（raw/03-transcripts/deep-research-report.md）
  │  贡献：编排模式系统分类、MCP/A2A 协议深度拆解、9×8 框架对比矩阵、实验设计方案
  │  盲区：行业最新动态（Anthropic 多 Agent 研究系统公开、Claude Managed Agents）、
  │        失败模式分析、Windows 实操可行性
  │
  ├── 交集 ──→ 五大多 Agent 编排模式分类一致
  │             MCP+A2A 双协议栈定位一致
  │             Manager-Worker（Hub-and-Spoke）被双方认定为核心模式
  │
  ├── 互补 ──→ 用户报告更学术、更系统（对比矩阵、Mermaid 图、实验设计）
  │            我的报告更行业、更实操（公司分析、Omega 映射、进化方案）
  │
  └── 共同盲区 → 补充报告中补上了失败模式、Windows 可行性、记忆持久化
```

**核心共识**：
1. **Manager-Worker（Orchestrator-Worker）是当前最成熟的多 Agent 模式**——被 Anthropic、OpenAI、DeepMind 三方独立验证
2. **MCP + A2A 构成 Agent 互联网的协议基础**——但对个人知识库场景，Agent Teams 的 P2P 邮箱 + 共享文件系统更实用
3. **「没有 Critic 的多 Agent 系统是危险的」**——DeepMind 的 17.2x 错误放大数据是最严厉的警告
4. **你的 Omega 设计被 2026 年行业全面验证**——这意味着设计方向正确，只是需要用现有工具「够用就好」地实现

## 1.2 关键架构决策

在进入构建计划之前，必须先明确以下架构决策：

### 决策 1：基础设施选择 —— Claude Code Agent Teams，而非 Omega 物理构建

| 选项 | 优点 | 缺点 | 判定 |
|------|------|------|:--:|
| **Omega 物理构建** | 完全自主、可定制 UI、独立于 Anthropic 生态 | 数月构建周期、需要维护完整代码库、Omega Terminal 需 Electron+React+FastAPI | ❌ |
| **Claude Code Agent Teams** | 零构建成本、与现有 vault 原生集成、P2P 邮箱+Git Worktree+共享任务列表 | 实验性功能（不稳定风险）、成本 3-4x、依赖 Anthropic 路线图 | ✅ |

**选择理由**：
- Agent Teams 提供的「独立上下文 + P2P 邮箱 + Git Worktree 隔离 + 共享任务列表」恰好覆盖了 Omega 的核心运行时需求
- 你的 vault 已经是 Git 仓库，天然支持 Worktree
- 如果 Agent Teams 不稳定或 Anthropic 方向变化，回退到 v11.0 只需关闭一个环境变量

### 决策 2：团队规模 —— 从 2 Agent 起步，上限 4 Agent

| Agent 数 | 通信复杂度 | 成本倍数 | 适合场景 | 判定 |
|:--:|---------|:--:|------|:--:|
| 1 | — | 1× | 顺序任务、简单操作 | 基线 |
| **2** | 1 条 P2P 通道 | **~2×** | Writer + Critic 对抗验证 | **Phase 1** |
| **3** | 3 条 P2P 通道 | **~3×** | + Researcher | **Phase 2** |
| 4 | 6 条 P2P 通道 | ~4× | + Knowledge Steward | Phase 3 |
| 5+ | N² 爆炸 | 5×+ | 仅大规模独立并行任务 | 暂不进入 |

**选择理由**：Anthropic 社区数据（3-5 是甜点）+ DeepMind 数据（2-5 Agent 最优）+ 你的任务特征（大部分是检索→阅读→提取→写作的链，天然并行度有限）

### 决策 3：Critic 角色 —— 必须使用不同的「激励函数」

这是从失败模式研究得出的最关键决策：

**单一栽培问题**：如果 Writer 和 Critic 使用同一个模型、同一套规则、同一个上下文来源——它们的盲区完全相同。Critic 会「从众附和」而非「独立验证」。

**解决方案**：
- Critic 的系统 prompt 必须**明确包含对立激励**：「你的工作是找到这个页面的问题。如果你找不到任何问题，说明你不够努力。默认假设是有问题需要发现。」
- Critic 的工具集应**区别于 Writer**：Critic 有权访问 WebSearch（验证外部事实）但无权 Write/Edit
- 理想情况下 Critic 使用不同模型（如 Writer 用 Sonnet、Critic 用 Opus），但 Agent Teams 当前同模型限制使这暂时不可行——用 prompt 工程弥补

### 决策 4：共享状态 —— Obsidian vault 文件而非内存

| 方式 | 优点 | 缺点 | 判定 |
|------|------|------|:--:|
| 内存/消息传递 | 低延迟、实时 | 会话结束丢失、Agent 间上下文污染 | ❌ |
| **vault Markdown 文件** | 天然持久化、Git 可追溯、Obsidian 可浏览 | 文件 I/O 延迟、并发写入需协调 | ✅ |

**选择理由**：你的知识库本质就是 Markdown 文件——让 Agent 像人一样「读写文件」来协作，保持知识库的透明性和可审计性。这也是 Omega「模拟真人助理」理念的延伸。

### 决策 5：记忆体系 —— 利用现有 wiki/ 而非新建后端

你的五层记忆**已经有四层在 Obsidian 中运行**：

| 记忆层 | Omega 设计 | v12.0 实现 |
|--------|-----------|-----------|
| L0 会话 | LangGraph State | Claude 对话上下文 |
| L1 情节 | Action Memory (Postgres) | `wiki/log.md` + 月度归档（已有） |
| L2 语义 | Qdrant + Neo4j | `wiki/实体/` + `wiki/概念/`（已有） |
| L3 程序 | Skill Library (Git) | `.claude/skills/` + `.claude/rules/`（已有） |
| L4 合规 | Postgres 审计分区 | 暂由 Critic Agent 维护的 `## 审计日志` 区块替代 |

**不需要新建数据库后端**——所有记忆已经在 vault 文件里。Agent 通过 Read/Write 工具访问，和你的交互方式完全一致。

# 第二部分：分阶段构建计划

## Phase 0：前提验证（本周，预计 2-3 小时）

> **目标**：确认「是否应该进入多 Agent」这个根本问题。
> **产出**：Go/No-Go 决策 + 单 Agent 基线数据。
> **成本**：零额外成本（不开启 Agent Teams）。

### Step 0.1：测量单 Agent 基线

```
操作：用当前单 Agent 模式 /ingest 10 篇未处理 raw 文件
记录：
  □ 总耗时（从指令到全部页面创建完成）
  □ 每篇的处理深度（D1/D2/D3 分布）
  □ 创建后需要人工修正的次数和类型
  □ 遗漏的核心事实数量（随机抽 3 篇与原文比对）
  □ Token 消耗量
  □ 主观满意度（1-10）
```

### Step 0.2：任务可并行性分析

```
操作：回顾最近 20 次 /ingest 或知识库操作
对每次操作标注：
  □ 任务类型（单篇摄取/批量摄取/lint/query/页面更新）
  □ 依赖链长度（A→B→C 需要几步顺序依赖）
  □ 是否有独立可并行的子任务？
  □ 如果有，占工作量的百分比？

判定标准：
  - 如果 ≥40% 的操作有可并行子任务 → 多 Agent 的并行加速有价值
  - 如果 <40% 但有 ≥60% 的操作质量可受益于 Writer/Critic 分离 → 多 Agent 的质量提升有价值
  - 如果两者都不满足 → 暂不建议多 Agent
```

### Step 0.3：基础设施验证

```
□ 确认 vault 是 Git 仓库：git status
□ 测试 Git Worktree：git worktree add ../vault-test main（然后删除）
□ 检查 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS 是否可设置
□ 阅读 Claude Code Agent Teams 最新文档（WebFetch）
□ 确认 Obsidian 在 Worktree 目录下的行为（索引是否正常、插件是否冲突）
```

### Step 0.4：决策门

```
全部通过 → 进入 Phase 1
任一不通过 → 报告具体问题，等待用户决策
可并行性不满足但质量提升有价值 → 仍可进入 Phase 1（重点验证 Writer/Critic 分离）
```

### Step 1.1：创建 Agent Profiles

**文件 1：`.claude/agents/writer.md`**

```markdown

role: Wiki 页面编译者
engine: claude
permission_level: 1  # 受限写——可创建/编辑 wiki/ 页面，不可删除
tools_allowlist: [Read, Write, Edit, Glob, Grep]
tools_denylist: [Bash(rm), Bash(git push)]

# Writer Agent — Wiki 页面编译者

## 身份
你是 OB 知识库的专业写作者。你的唯一职责是将原始信息和研究成果编译为高质量的 wiki 页面。

## 核心规则
1. 严格遵守 CLAUDE.md 中的页面模板规范
2. 所有页面必须包含完整 frontmatter
3. wikilink 出链 ≥3 条（含 ≥1 概念页）
4. 信息分解标记（🔴🟡🟢⚪）必须逐段标注
5. **绝不静默修改已有页面**——修改前必须标注变更内容
6. 页面完成后，将文件路径写入共享任务列表标记为「待审查」

## 禁止行为
- 不验证事实——那是 Critic 的工作（但你知道的事实应该写准确）
- 不删除文件——除非用户明确指令
- 不与 Critic 争论——接受审查结果，修改后重新提交

## 输出格式
每个完成的页面必须在末尾追加：
> 📝 待审查：请 Critic 验证以下方面：[列出关键声明]
```

**文件 2：`.claude/agents/critic.md`**

```markdown
---
agent: critic
role: 知识库质量审查者
engine: claude
permission_level: 0  # 只读 + 可追加审查报告
tools_allowlist: [Read, Grep, Glob, WebSearch, Write(critic-reports/)]
tools_denylist: [Write(wiki/), Edit]
---

# Critic Agent — 知识库质量审查者

## 身份
你是 OB 知识库的独立质量审查者。你的工作是找到页面的问题——如果找不到问题，说明你不够努力。

## 核心激励
**默认假设：每篇页面都有可改进之处。** 你的价值在于发现问题，而非确认正确。

## 审查清单（逐项检查）
1. **事实准确性**：用 WebSearch 或已有知识库验证 ≥3 条核心声明
2. **引用完整性**：每条 🔴 核心事实是否有来源追溯
3. **逻辑一致性**：页面内部和与其他页面的关系是否有矛盾
4. **格式合规性**：frontmatter 是否完整、wikilink 出链是否 ≥3
5. **遗漏检测**：与原始资料比对，是否有 🔴 核心事实未被覆盖
6. **单一栽培检查**：你是否因为和 Writer 用同一模型而忽略了某些问题？

## 审查报告格式
```markdown
## Critic 审查报告 — [页面名]

### 发现
- 🔴 严重问题（事实错误/遗漏/矛盾）：N 条
- 🟡 改进建议（格式/链接/可读性）：N 条
- 🟢 确认无误：N 条

### 逐项详情
[每条问题的具体描述 + 修正建议]

### 总体评分：X/10
□ 通过（≥8） □ 需修正（5-7） □ 需重写（<5）
```

## 禁止行为
- 不修改 wiki/ 页面——你只能审查，不能写
- 不为了「找到问题」而编造不存在的问题
- 不过度挑剔格式细节忽视实质内容
```

```

### Step 1.4：Phase 1 决策门

```

    - 单一栽培问题（同模型盲区重叠）

□ 质量提升是否值得 2× token 成本？
  → 是 → 继续
  → 否 → 可能需要仅在「高价值页面」上使用 Critic

□ 协作流程是否顺畅？
  → 是 → 进入 Phase 2
  → 否 → 优化流程后重新测试
```

# Researcher Agent — 信息检索与知识提取者

## 身份
你是 OB 知识库的专业研究员。你的工作是深入阅读原始资料，提取结构化知识卡片，为 Writer 提供「即用型」素材。

## 工作流程
1. 接收 Team Lead 分配的 raw 文件路径
2. 深度阅读源文件（D3 精读标准：逐段信息分解 🔴🟡🟢⚪）
3. 产出「知识卡片」——结构化摘要，包含：
   - 核心主题（1 句话）
   - 关键发现（🔴 级，逐条标注）
   - 方法学要点（如适用）
   - 与其他已有知识的关联（搜索 wiki/ 找 wikilink 候选）
   - 建议的页面类型和 tags
4. 将知识卡片写入 `.claude/cache/research-cards/<slug>.md`
5. 通过 P2P 邮箱通知 Writer：「卡片已就绪」

## 核心规则
- 不与 Writer 争论页面怎么写——你只提供素材
- 不确定的事实标注「待验证」
- 发现与其他 wiki 页面矛盾时，在卡片中高亮标注

## 输出格式
```markdown
# 知识卡片：[主题]

## 核心主题
[一句话]

## 关键发现
- 🔴 [发现 1]
- 🔴 [发现 2]
- ...

## 方法学要点
- ...

## wiki 关联
- 已有页面：[[页面A]]、[[页面B]]
- 建议新建：（施工占位符已清理，2026-06-03 lint 修复）

## 元数据
- 来源：[raw 文件路径]
- 深度：D3 精读
- 信息密度：高/中/低
- knowledge_stability: stable/evolving/timely
```

  Researcher 2 → 文件 B 的知识卡片  ← 通过 Agent Teams 并行

```

```

## 3.2 典型工作流：从用户指令到知识入库

### 场景：用户说「帮我把这 3 篇新文献处理了」

```
Step 1: Team Lead 接收指令
  ├─ 扫描 raw/ 确认文件存在
  ├─ 初步评估：3 篇都是医学论文，IF 较高 → 建议 D3 精读
  └─ 写入 active-board.md

Step 2: Researcher Agent 开始工作（3 篇并行）
  ├─ Researcher 1 → 论文 A：PDF 提取 → 全文精读 → 知识卡片
  ├─ Researcher 2 → 论文 B：PDF 提取 → 全文精读 → 知识卡片
  └─ Researcher 3 → 论文 C：PDF 提取 → 全文精读 → 知识卡片
  耗时：~8 分钟（并行）vs ~24 分钟（顺序）

Step 3: Writer Agent 创建页面（顺序，避免文件冲突）
  ├─ 读取知识卡片 A → 创建 [[来源/论文A]]
  ├─ 读取知识卡片 B → 创建 [[来源/论文B]]
  └─ 读取知识卡片 C → 创建 [[来源/论文C]]
  耗时：~6 分钟

Step 4: Critic Agent 审查
  ├─ 审查 [[来源/论文A]]：发现 1 个引用缺失 → 评分 8/10
  ├─ 审查 [[来源/论文B]]：通过 → 评分 9/10
  └─ 审查 [[来源/论文C]]：发现 2 个事实遗漏 → 评分 6/10 → 需修正
  耗时：~5 分钟

Step 5: Writer 修正 + Critic 重新审查
  └─ 修正 [[来源/论文C]] → Critic 重新评分 9/10

Step 6: Steward Agent 收尾
  ├─ 更新 wiki/index.md（3 个新页面入表）
  ├─ 更新 wiki/log.md（操作日志）
  └─ 检查 wikilink 一致性

总耗时：~25 分钟（3 篇 D3 精读 + 页面创建 + 审查）
单 Agent 耗时：~40 分钟（同样工作量）
质量提升：Critic 捕获了 3 个单 Agent 会遗漏的问题
```

## 3.3 与 Omega 的关系：什么被构建了，什么被推迟了

- 11 个专职 Agent 的完整部署

- 完整的自动化评测流水线

## 3.4 成功指标

| 指标 | 当前（v11.0 单 Agent） | 目标（v12.0 多 Agent） | 测量方式 |
|------|:--:|:--:|------|
| **页面质量评分** | Critic 不可用，无系统评分 | ≥8.0/10 平均分 | Critic 审查报告 |
| **首次通过率** | 人工检查，无系统数据 | ≥60% 页面首次审查即通过 | Critic 评分 ≥8 的比例 |
| **错误捕获率** | 依赖用户事后发现 | ≥80% 错误在 Critic 阶段被捕获 | Critic 发现 vs 用户后续发现 |
| **并行加速比** | 1×（顺序处理） | ≥1.5×（对可并行任务） | Phase 0 基线 vs Phase 2 实测 |
| **人工修正次数** | 每次 /ingest 平均 N 次 | ≤N/2（减少 50%） | log.md 中的 update 条目 |
| **知识库一致性** | /lint 绿灯率 | /lint 绿灯率保持或提升 | /lint 报告 |
| **用户满意度** | 主观 | 主观提升 | 用户直接反馈 |

## 3.5 不变的核心约束

无论架构如何演进，以下原则**不可触碰**（来自现有合规监察 + 处理诚信 + 反自问自答协议）：

| 约束 | 在多 Agent 中的保障 |
|------|-------------------|
| **用户最终决策权** | 所有敏感操作必须用户审批；Agent 不替代用户做不可逆决策 |
| **知识库写入需确认** | Writer 不静默修改已有页面；变更需 Critic 审查 + 用户可见 |
| **禁止虚假申报** | 每个 Agent 的处理深度声明可被 Critic 独立验证 |
| **验证先于宣称** | Critic 不「声称已验证」而未实际比对原文 |
| **反自问自答** | Agent 间通信不产生面向用户的输出；Team Lead 是唯一用户界面 |
| **安全删除** | 删除操作仅 Team Lead 可执行（需用户确认）；Worker Agent 无删除权限 |
