## 阶段 10：从“能力存在”转向“能力激活”（2026-06-12 → 2026-06-17）

这一阶段的审计揭示了知识库最重要的一次认知纠偏：系统的瓶颈不再是“缺少能力”，而是发现、路由、激活、执行和验证之间存在断裂。历史快照曾记录 764 个注册 Skills 中仅 117 个可调用、46 个脚本利用率约 33%、8 个 Agent Profile 中仅 3 个活跃、7 个 MCP 中有 2 个故障，合规评分一度为 57/100。这些数字属于当时的诊断快照，不作为当前状态。

### 已确认的演进

- 引入能力注册表和会话启动发现，减少“磁盘上存在、上下文里不可见”。
- 建立上下文路由、强制激活门和架构版本守卫，连接“发现→激活→使用”。
- 将批量任务、Agent 配额、Computer Use 巡检、跨领域链接和工具降级纳入统一执行协议。
- 用执行清单推动 Phase 0 止血，包括注册表、Skill 索引、会话启动注入、记忆实现统一和工具优先级纠偏。
- 形成关键经验：能力目录只能证明库存，真实调用和用户结果才证明系统能力。

---

## 阶段 11：Ω-Loop 与执行闭环（2026-06-16 → 2026-06-19）

**核心命题**：规则、工具和 Agent 需要通过统一事件、状态和质量门形成可观察闭环。

知识库把早期分散的 Hook、任务卡、Agent 调度、合规检查和进化提案收敛为五层结构：资源层、钩子层、事件总线、编排层和自进化层。Ω-Loop 的价值不在于增加一个新品牌，而在于确立“事件可追踪、状态可恢复、失败可传播、输出可审计”的执行纪律。

### 已确认的经验

- 先统一规则冲突和状态语义，再增加自动化。
- 自动化必须有停止条件、人工批准门和失败关闭路径。
- Writer/Researcher/Critic 的角色名称不重要，输入输出合同、依赖顺序和独立审查才重要。
- 长任务应保存结构化状态，而不是依赖不断膨胀的聊天上下文。

专题实现继续保留在 [[洞察/Ω-Loop生态系统架构]] 和 [[洞察/Ω-Loop最终执行方案]]，本页只保存历史结论。

## 阶段 12：成本、上下文与知识供给治理（2026-06-30 → 2026-07-10）

**核心命题**：知识和工具越多，检索噪声、常驻上下文与 Token 成本越可能抵消能力收益。

这一阶段开始从“尽可能多地加载”转向“按任务路由最小必要上下文”。知识库对常驻规则、工具描述、重复研究、外部项目和多 Agent 成本进行测量，形成智能路由、分层发现、图谱化代码发现和质量优先的上下文控制策略。

### 已确认的经验

- 先用文件名、索引、图和结构化摘要定位，再读取正文。
- 当前任务只加载当前合同和最小相关证据，不继承全部历史对话。
- 同一知识不应同时以原始日志、多个版本方案、重复摘要和聊天会话四种形式长期保存。
- 节省 Token 的正确方式是减少重复和无关上下文，而不是降低科研或安全标准。

量化方法和工具核验继续保留在 [[洞察/知识库工作流省token与性价比优化]]。

## 阶段 13：跨 Agent 兼容与生产融合（2026-07-18 → 2026-08-25）

**核心命题**：知识库不能依赖单一 Agent、单一模型或单一界面；能力必须在真实产品链路中可发现、可调用、可恢复。

系统开始系统化处理 Claude/Codex、Obsidian 插件、Skills、MCP、Agent Team、Zotero、WeKnora、模型发现和跨平台工具之间的兼容问题。执行方式从单点脚本验证升级为真实 Obsidian 冷启动、连续多轮、实际 Vault、审批卡、外部工具、取消恢复和生产部署的全链路验收。

### 已确认的进步与边界

- Codex/Claudian 生产插件形成可构建、可备份、可哈希核对和可恢复部署的工程链路。
- Skills、模型配置、MCP 安全审批和多 Agent 管道开始使用同一生产身份做证据绑定。
- 认识到“单元测试通过”“runner 文件存在”“历史版本曾 PASS”都不能替代当前生产哈希上的真实用户证据。
- 跨 Agent 兼容的首要问题通常不是模型能力，而是身份、事件顺序、工具合同、错误投影和清理生命周期。

仍有效的实现蓝图保留在 [[洞察/知识库工作流全量修复与跨Agent兼容性蓝图]]。

## 阶段 14：最小证据、错题集与磁盘治理（2026-08-26 起）

**核心命题**：完整保留每次迭代的聊天、profile、构建包和重复证据，会制造空间债务、检索噪声和新的推理成本。

生产验收暴露出一种新的系统性失败模式：多代理会话将完整父上下文复制进大量子会话，单个原始 JSONL 可达到 1.3–1.4 GB；同时项目目录保留多代生产包、临时 Obsidian profile 和已被终态替代的 Round。知识并没有因此更可靠，反而更难找到当前事实。

### 新治理原则

1. **单一当前真相源**：当前生产、当前账本、当前 manifest/validator/handoff。
2. **错题卡**：每个问题只记录症状、影响、证据承诺、根因状态、修复动作和关闭条件。
3. **最小复现**：每题只保留最新 actionable FAIL、最新 PASS 和最多一张必要截图。
4. **单一恢复点**：生产只保留当前版本和一个直接前驱备份。
5. **不可变基准**：只有明确具有审计价值的基准永久保留。
6. **原始日志短期化**：结论进入错题卡或本历程后，重复会话、旧 profile、nonce、旧 build 和过时 receipt 立即淘汰。

2026-08-26 已完成三轮治理：第一轮清理 1,178 个已核验的 WP10 临时/旧版本目标，实际回收约 1.03 GiB；第二轮将 248 个已停止、可追溯到仍被保留根任务的超大子代理 JSONL 浓缩为元数据清单后删除，逻辑文件大小 187.69 GiB，D 盘可用空间由约 7.38 GiB 恢复到约 187.48 GiB；第三轮删除 C 盘 Temp 中 14 个固定旧诊断、安装包和工具解压目标，实际释放 7.24 GiB。由此确认，主要空间债务来自完整上下文在子代理会话中的重复复制和无生命周期的临时产物，而不是 Obsidian 知识正文。所有根任务、当前任务和仍在活动的会话均保留。开放错误继续暂留项目错题集，待完整生产任务完成后再把稳定经验并入本页。
