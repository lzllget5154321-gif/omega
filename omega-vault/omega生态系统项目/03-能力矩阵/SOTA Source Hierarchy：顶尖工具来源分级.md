# SOTA Source Hierarchy：顶尖工具来源分级

> **定位**：规定 Omega 在查找工具、模型、Skill、代码、教程、最佳实践时，不同来源的信誉权重和验证要求。让 Omega 既能大胆吸收外部信息，又不会被低质量内容牵着走。

---

## 一、为什么需要来源分级

Omega 的核心能力之一是"感知外部世界"。但如果对所有来源一视同仁——把营销软文和官方文档同等对待——系统就会被噪音污染。

来源分级的核心原则：

> **社交平台发现信号 → 官方文档确认能力 → 代码/GitHub 验证可用性 → 沙箱测试决定是否纳入 → 信誉系统追踪长期表现。**

---

## 二、四级来源体系

### S0：官方与权威来源（权重 1.0，直接信任）

| 来源类型 | 具体来源 | 可获取的信息 | 验证要求 |
|---------|---------|------------|---------|
| **官方文档** | 工具的 docs.xxx.com / readthedocs.io | API 参考、参数说明、能力边界、限制 | 无需额外验证 |
| **官方 API 文档** | OpenAPI/Swagger/GraphQL schema | 端点、请求/响应格式、认证方式 | 无需额外验证 |
| **官方 GitHub 仓库** | github.com/<org>/<repo> | README、源码、Issues、Release Notes | 区分官方仓库 vs 社区 fork |
| **官方 Release Notes** | GitHub Releases / 官方博客 / Changelog | 版本变更、新功能、破坏性变更、弃用通知 | 无需额外验证 |
| **官方 Discord/论坛/博客** | 官方运营的社区和博客 | 路线图、已知问题、最佳实践、官方示例 | 标注"非正式文档" |
| **模型/工具官方公告** | Anthropic/OpenAI/Google/Meta 等官方渠道 | 新模型参数、定价、API 变更、能力声明 | 区分公告 vs 实际能力 |

### S1：代码与工程实践来源（权重 0.85，需代码验证）

| 来源类型 | 具体来源 | 可获取的信息 | 验证要求 |
|---------|---------|------------|---------|
| **高质量 GitHub 项目** | Stars ≥ 500 + 活跃维护 | 实际使用方式、工程实践、边界处理 | 检查代码质量 + 沙箱验证 |
| **GitHub Trending** | trending 页面 | 新兴工具和项目 | 区分热度 vs 成熟度 |
| **GitHub Issues/PRs** | 项目的 Issues 和 Pull Requests | 已知 bug、社区修复、使用技巧 | 交叉验证（多个 Issue 同问题） |
| **Hugging Face 模型页** | huggingface.co/models | 模型参数、性能基准、使用示例 | 沙箱测试模型实际表现 |
| **PyPI / npm / conda** | 官方包注册表 | 版本、依赖、下载量、发布时间 | 检查维护状态 + CVE |
| **官方示例代码** | 仓库中的 examples/ 目录 | 正确使用方式、参数配置 | 沙箱运行验证 |

### S2：高质量社区实践（权重 0.55，需交叉验证）

| 来源类型 | 具体来源 | 可获取的信息 | 验证要求 |
|---------|---------|------------|---------|
| **YouTube 高质量教程** | 官方频道 / 知名技术 YouTuber | 实操演示、工作流、技巧 | 比对官方文档 + 检查评论区反馈 |
| **X/Twitter 核心开发者** | 模型作者、工具维护者、核心贡献者 | 最新动态、未文档化技巧、路线图透露 | 确认账号真实性（verified + bio检查） |
| **微信公众号（技术类）** | 官方号、开发者号、实验室号、技术号 | 中文技术解读、实操教程 | 区分技术号 vs 营销号 |
| **Bilibili 教程** | 官方号 / 知名 UP 主 | 中文视频教程、实操 | 与官方文档比对 |
| **Reddit / Discord 实践反馈** | r/MachineLearning 等技术社区 | 真实使用体验、避坑、对比 | 关注"多人确认"的信号 |
| **技术博客（个人/公司）** | 知名技术博客 | 深度分析、对比评测 | 检查是否有代码/数据支撑 |
| **arXiv / 会议论文** | 学术论文 | 方法原理、基准测试、理论分析 | 区分预印本 vs 已发表；区分 AI 生成论文 |
| **GitHub Gist / 代码片段** | 社区分享的代码 | 特定问题解决方案 | 沙箱测试 |

### S3：泛社交与未验证信号（权重 0.20，仅作趋势发现，不直接采用）

| 来源类型 | 具体来源 | 可获取的信息 | 验证要求 |
|---------|---------|------------|---------|
| **普通自媒体** | 非官方/非知名账号 | 工具推荐、评测 | 必须经 S0/S1 来源交叉验证 |
| **未验证教程** | 来源不明 / 匿名 | 使用教程 | 除非有 S1 代码验证，否则不采用 |
| **转载内容** | 二手信息、中文翻译 | 间接信息 | 追溯到原始来源 |
| **"爆火但缺验证"的工具** | 社交媒体病毒传播 | 趋势信号 | 标记为 hype，等待 S0/S1 验证 |
| **AI 生成的评测/教程** | 不确定是否人工撰写 | 不可靠 | 必须交叉验证多个来源 |

## 三、来源信誉衰减规则

随着时间推移，来源的信誉自然衰减：

| 来源类型 | 新鲜度窗口 | 衰减速度 | 过期判定 |
|---------|-----------|---------|---------|
| **官方文档** | 持续有效 | 仅在版本升级时衰减 | 对应版本过时时 |
| **Release Notes** | 1 个月 | 快速 | 新版本发布后旧版本 notes 参考价值降为 0.3 |
| **GitHub Issues** | 3 个月 | 中等 | 关闭超过 6 个月的 issue 权重降至 0.2 |
| **YouTube 教程** | 6 个月 | 中等 | 超过 1 年的教程需标注"可能过时" |
| **X/Twitter 帖子** | 1 周 | 极快 | 超过 1 个月的帖子降为"历史参考" |
| **微信文章** | 1 个月 | 快速 | 超过 3 个月降权 50% |
| **Reddit 讨论** | 2 周 | 快速 | 超过 1 个月的帖子降为参考 |
| **arXiv 预印本** | 6 个月 | 中等 | 未被正式发表的 2 年后降权 |
| **社交媒体病毒传播** | 3 天 | 极快 | 一周后降为噪音 |

## 四、多源交叉验证协议

### 4.1 验证强度

| 验证组合 | 强度 | 含义 |
|---------|------|------|
| S0 单一来源 | 🟢 高 | 官方文档/API 可直接信任 |
| S0 + S1 交叉验证 | 🟢🟢 极高 | 官方文档 + 代码验证 |
| S1 单一来源 | 🟡 中 | 需要沙箱确认 |
| S0 + S2 交叉验证 | 🟡 中高 | 官方文档 + 社区实践一致 |
| S2 单一来源 | 🟠 低 | 需要 S0 或 S1 确认 |
| S2 × 3 不同来源一致 | 🟡 中 | 多方社区一致，可提升信任 |
| S2 + S3 一致 | 🟠 低 | 仍需 S0/S1 |
| S3 单一来源 | 🔴 不可信 | 仅作信号，不纳入决策 |

### 4.2 矛盾处理

```
S0 官方文档 与 S2 社区实践 不一致？
  → 以 S0 为准
  → 但仍记录社区发现的问题（可能是未文档化的 bug）

S0 官方文档 与 S0 官方 Release Notes 不一致？
  → 以最新的为准
  → 标记为"文档滞后"

S1 代码仓库 与 S2 教程 不一致？
  → 以代码仓库实际运行为准
  → 教程可能过时

S2 多个社区来源互相矛盾？
  → 标记矛盾
  → 沙箱实测决定
  → 记录为 Tool Reputation Ledger 的矛盾条目
```

## 五、来源发现与 SOTA 追踪

### 5.1 "SOTA 是什么"的自动判断

当 Omega 需要回答"这个领域当前最好的工具/方法是什么"时，来源分级自动决定答案的置信度：

```
问题："医学教学动画制作，现在最好的工具是什么？"

来源扫描：
  S0: Blender 官方文档（4.2 的功能）         → 高置信
  S0: Manim 官方文档（v0.18 社区版）          → 高置信
  S1: GitHub — ComfyUI 社区工作流            → 中高置信
  S1: GitHub — 医学可视化项目的依赖分析        → 中高置信
  S2: YouTube — 5 个医学动画制作教程          → 交叉验证
  S2: Reddit r/MedicalIllustration 讨论       → 交叉验证
  S3: X 上某账号说"XX 新工具是最佳"           → 仅信号

答案合成：
  1. Blender（S0 + S1 验证）→ 最推荐用于 3D 细胞动画
  2. Manim（S0 + S1 验证）→ 最推荐用于 2D 可解释动画
  3. ComfyUI（S1 社区工作流）→ 值得关注的可控视觉方案
  4. X 上的新工具推荐 → 仅记录，等待 S0/S1 验证

置信度标注：
  - 前 2 个工具为高置信（S0 + S1）
  - ComfyUI 为中置信（S1，未达 S0 官方文档级别）
  - 未经验证的推荐不纳入"最好"判断
```

### 5.2 防止"追新"陷阱

```
规则：SOTA ≠ 最新。SOTA = 经过验证的当前最佳。

发现一个新工具（S2 热传）：
  1. 记录到雷达
  2. 标记 hype 状态
  3. 等待 2-4 周 → 看是否持续获得 S1/S2 关注
  4. 如果有 S0 官方来源或 S1 高质量代码 → 进入评估
  5. 如果热度消退 → 降级为 watched

示例：
  "X 上都在说 Tool-Y 是 Blender 杀手"
  → Omega 记录信号
  → 2 周后：没有官方文档、没有 GitHub 高星项目、热度消退
  → Omega 标记："hype not validated, watching"
  → 不会推荐给用户
```

## 六、与现有组件的接口

```
SOTA Source Hierarchy
  │
  ├──→ AI工具生态雷达：决定新发现工具的初始信誉权重
  ├──→ Toolsmith-Lite：决定试用工具的优先级（S0/S1 优先）
  ├──→ Best-Practice Harvester：决定最佳实践的来源选择
  ├──→ Social Signal Validator：输入社交信号的验证标准
  ├──→ Tool Reputation Ledger：来源权重影响工具信誉计算
  └──→ Tool-Agent Router：SOTA 判断影响工具推荐的置信度标注
```
